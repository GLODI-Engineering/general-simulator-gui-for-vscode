## 2026-11-05 (later) — rendering made grid-exact, a .vsix that installs, and a Python front end

**Branch:** `main` — commits `44f75d3`, `b689edf`, `120b291`

### Rendering

Every fix in `44f75d3` was found by rendering the buck converter and looking
at it, not by a failing test. The root cause of most of the geometry defects
was one thing: `SYMBOL_SCALE` 1.6 and `STUB_LEN` 16 against a `GRID` of 20,
so a port centre landed at 32 and a two-terminal part spanned 128 — nothing
on grid, ever. At scale 2 with a one-grid lead the arithmetic closes and
every terminal sits on an intersection. `wire-path.ts`'s six-pixel
`ORTHOGONAL_TOLERANCE_PX` and `snapNearOrthogonal` exist to hide the old
mismatch and can probably go now.

`STUB_LEN` was declared twice — `Port.tsx` draws the lead, `port-hit-test.ts`
decides where the wire attaches to it — and I changed one of them before
noticing, which would have put every wire four units short of its lead.

Junction dots were computed from waypoints only, which misses both real
cases: three wires meeting at a shared port (no wire has three vertices
anywhere) and a wire bending onto another's segment, which is how a rail is
tapped.

`examples/buck_converter.gsim_sch` is the reference sheet. Writing it
exposed that the canvas drops a wire naming a non-existent port in silence —
the diode's pins are `a`/`k`, the generator said `p`/`n`, and the render came
out missing its freewheel path. Now issue #2.

### The .vsix

Renaming the manifest changed the extension id and broke the integration
suite, which had the old literal in three more places. Centralising it
uncovered a nastier bug: `getTestApi` held its result in a local called
`exports`, and this file compiles to CommonJS where a module-level
`export const` is emitted as `exports.NAME` — so every reference to
`EXTENSION_ID` resolved to that local and hit its temporal dead zone.

`pnpm package` now builds, bundles the webviews into `media/frontend` (the
only root `webview-content.ts` probes that survives `vsce package`) and
writes the .vsix. Verified: it installs via `code --install-extension` into
an isolated extensions dir, and the integration suite passes against a real
VS Code 1.145.0 — **14 passing**. The kernel sidecar reaches `KERNEL_READY`
via `uv run --project . --package kernel-sidecar`.

### The port-domain bug

Generating the same buck converter through the new Python package produced
grey wires where the hand-written sheet produced black. Cause: 136 port
declarations across 55 metadata files said `kind: { domain: electrical }`.
That is `behavior.domain`'s enum, not `PortKindDomain`'s, where the value is
`physical-electrical`. Both fields are called `domain` and sit a few lines
apart in the same file, and nothing validated it — about a fifth of all
electrical parts drew in the unknown-domain grey and failed port-compatibility
against correctly-spelled parts. Fixed at source, manifest regenerated,
`catalog-port-domains.test.ts` added as the guard.

Worth noting how this was found: not by reading the metadata, but because an
independent implementation disagreed with the first one.

### Python front end

`general-simulator-python` (local, not yet pushed — repo creation was
blocked). `gsim.geometry` mirrors this repo's geometry contract exactly, and
the buck converter it generates renders identically to the hand-authored one.
It refuses what this canvas accepts and then draws wrongly: unknown port,
off-grid placement, overlapping bodies, diagonal wires. A real RC step
response through the engine matches `10*(1-exp(-t/RC))` to four figures.

### What's left

- Labels still anchor to the bbox rather than the ink, so a value sits
  further from a thin glyph than it should (issue #1).
- Issue #2: surface unresolvable wire endpoints as VS Code diagnostics.
- Custom symbols still do not persist — `saveSymbolToLibrary()` writes to the
  in-memory catalog only, and an authored symbol carries no behaviour.
- The docs still name commercial tools in ~30 places; that is a public-flip
  blocker, not a private-repo one.

## 2026-11-05 — repo split: a VS-Code-only GUI, forked clean from general-simulator-gui

**Branch:** `main` (initial commit)

The previous repo (`general-simulator-gui`, kept private) tried to be three
products from one tree: a web app, a Tauri desktop app and a VS Code
extension. The user's call was to fork it, keep the old one private as the
failed attempt, and let the new repo target VS Code and nothing else.

### What was carried over, and what was not

The old tree was not rubble — every gate was green before the fork
(frontend build, 778 frontend tests, 25 extension tests, extension
typecheck). So this is a prune, not a rewrite. Of 1 387 tracked files,
1 304 came over and 83 were dropped:

- `apps/desktop/` (Tauri shell) and the three `@tauri-apps/*` dependencies.
  The coupling was 17 files and 67 references, all behind a clean adapter —
  `select-adapter.ts` now returns `IndexedDbAdapter` unconditionally, and
  `transport.ts` lost `initKernelFromTauri()` / `runTauriConnect()` and the
  `invoke("restart_kernel")` branch of `reconnectKernel()`.
- `apps/api/` — five files, every one an empty `__init__.py`.
- `src/explorer/`, `src/search/`, `src/output/` — webview reimplementations
  of surfaces VS Code already provides. `explorer` and `search` registered
  into `ActivityRegistry`, which nothing renders under VS Code (there is no
  `PrimarySideBar`), so they were already dead code.
- The Archon epic machinery: `progress.{frontend,backend,bugs}.yaml`
  (870 KB), `.archon/`, `.opencode/`, `.pi/`, `scripts/aw-*`, and the five
  loop-driver skills. Work is tracked as GitHub issues here. Note this
  discards the record of which epics were unsigned-off — 21 frontend and 18
  backend epics sat at `status: review`, implemented but never reviewed.
- Stale docs: the old journal months, `CODEBASE-SUMMARY.md`, the May release
  notes, the frontend release audit/checklist, and the four Archon/pi-specific
  gotchas (004 and 006 are generic and were kept).

### Two things the cut broke, both fixed

- `src/tauri-modules.d.ts` also carried the `*.svg?react` declaration for
  `vite-plugin-svgr`. Deleting it broke `tsc` on
  `component-symbols.tsx`'s PMOS import. Split out as `src/svg.d.ts`.
- `playwright-config.test.ts` asserted the four-project web/desktop matrix.
  The matrix is now three browser engines against the harness, with no

### Rendering: a harness, and a first honest look

The user's primary complaint is that schematics render ugly. The checked-in
evidence (`docs/circuit_test/buck_converter/frontend_buck_schematic.png`,
June) shows diagonal wires, hairline strokes and stray stubs — but that
image is five months old and several fixes behind, so it is not evidence
about today's code.

`scripts/render-schematic.mjs` was written to end that problem: it boots the
Vite preview, drives the harness through `__gensim_load_document` and
`__gensim_canvasFitView`, and writes a 2× PNG of the canvas. Rendering
quality cannot be unit-tested — no assertion sees two overlapping labels —
so the rule (AGENTS.md invariant 6) is that rendering work is not done until
someone has looked at the output.

Rendering the buck converter on current code shows real progress since June:
**wires are orthogonal, strokes are firm and dark, junction dots are drawn.**
What is still wrong, from the render:

1. Terminal leads are far too long, so components float apart from the
   circuit instead of sitting in it. `Port.tsx`'s `STUB_LEN = 16` is in
   *screen* units, outside `BlockSymbol`'s `scale(SYMBOL_SCALE = 1.6)` —
   the two unit systems are not reconciled.
2. Pin names (`p`, `n`, `c+`, `c−`, `A`, `K`, `+`, `−`) are drawn on every
   terminal. A finished schematic never shows pin names on two-terminal
   passives.
3. Value labels sit far from their symbols — `100 µH` floats in open space —
   because `labelAnchorFor` anchors to the bbox, which is much larger than
   the drawn glyph.
4. No reference designators (`V1`, `L1`, `C1`, `R1`, `D1`).
5. The dotted grid is visually noisy at render density.
